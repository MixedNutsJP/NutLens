# ADR-0032. 署名は「しないかもしれないもの」として扱い、特定のサービスに寄せない

- 状態: **採用**（2026-11-14 承認）
- 日付: 2026-11-14
- 置き換える対象: [ADR-0031](0031-release-from-tags-and-leave-a-slot-for-signing.md) の決定 4・5

## 背景

ADR-0031 の決定 4 は、署名の段を **SignPath のアクションとして**コメントで置いた。
D-10 が「**SignPath Foundation への申請**を前提に」と書いているためである。

承認の後、利用者から前提が違うと伝えられた。

> 署名は今後するか分からないし、SignPath を使用するとも限らないです

これは要件（D-10）の前提そのものが変わったということなので、
**ADR-0031 を書き換えずに、この番号で置き換える**（CLAUDE.md §3：
覆すときは新しい番号で起こす）。

決め直すのは次の 3 つ。

1. ワークフローに特定の署名サービスの名前を残してよいか
2. `CODE_SIGNING_POLICY.md` に何を書くか（**まだ決めていないことを、決めたように書かない**）
3. 署名が無いまま配ることを、利用者にどう伝えるか

## 決定

### 1. ワークフローに署名サービスの名前を書かない

ADR-0031 決定 4 の、SignPath のアクションをコメントで置く形をやめる。
代わりに、**何も呼ばない空の段**を置く。

```yaml
      - name: Build
        run: dotnet publish ...

      # --- 署名の段（いまは何もしない） ---
      #
      # 署名する場合は、ここに署名の処理を入れる。
      # **位置は動かさない。** publish の後、vpk pack の前。
      # 逆にすると、パッケージの中身を署名した後で再梱包することになり、署名が壊れる。
      #
      # 必要な資格情報は GitHub Actions のシークレットで渡す（D-14）。
      # ワークフローのファイルには書かない。

      - name: Pack
        run: vpk pack ...
```

**残すのは「位置」と「位置を動かすと壊れる理由」だけ。**
どのサービスを使うかは、使うと決めたときに決める。

名前を書いたまま置くと、**決めていないことが決まったように見える。**
半年後に読んだ人は「SignPath を使う方針だ」と受け取る。

### 2. `CODE_SIGNING_POLICY.md` には**現状**を書く

D-10 は「署名の方針を `CODE_SIGNING_POLICY.md` にまとめる」と言っている。
**ファイルは要る。** 中身を「SignPath に申請する方針です」にしない。

書くこと:

| 項目 | 内容 |
|---|---|
| 現状 | **署名していない。** そのため SmartScreen の警告が出る |
| 予定 | **決まっていない。** 署名するかどうかも、どの方式かも |
| 利用者が確かめる手段 | 成果物の出どころ（タグ・ワークフローの実行・コミット）を Releases から辿れること |
| 自己署名を使わない理由 | 警告は消えず、**「署名されている」という誤った安心だけが残る** |

**「未定」と書くことが、この文書の役目。**
空にしたり、やる予定のように書いたりしない。

### 3. 署名の代わりに「出どころを辿れること」を担保する

署名が無くても、**どのソースからどう作られたか**は示せる。

- リリースの成果物は GitHub Actions でしか作らない（ADR-0031 決定 1。**これは変えない**）
- どのタグ・どのコミット・どの実行から作られたかを、リリースノートに書く
- ビルドの記録は Actions に残り、誰でも見られる

**署名サービスが成果物に求めるのも、元はこの性質である。**
だから ADR-0031 決定 1（手元ビルドを使わない）は、
署名をやめても**守る価値がそのまま残る。**

### 4. README には「未署名である」とその影響を書く

ADR-0031 決定 5 から変える点は 1 つだけ。
**「承認されるまでは」と書かない。** 承認されるかどうかが未定だから。

```
NutLens は現在コード署名をしていません。そのため、インストーラーを実行すると
Windows の SmartScreen が警告を出します。
```

回避手順（「詳細情報」→「実行」）と、**なぜ出るのか**は引き続き書く。

## 影響

- `.github/workflows/release.yml` から SignPath の記述が消える
- `CODE_SIGNING_POLICY.md` の中身が「申請する方針」から「未定」に変わる
- **ADR-0031 の決定 1・2・3・6・7 はそのまま効く**（タグ駆動・版の取り方・秘密情報の扱い・
  配布の値を 1 箇所に集める）
- D-10 の「SignPath Foundation への申請を前提に」は満たさなくなる。
  **要件からの意図的な逸脱**として、トレーサビリティ表に残す

## 実装で分かったこと（2026-11-14）

### 1. 空の段は「位置」と「理由」だけになった

`release.yml` の署名の段には、呼ぶものが何も無い。
残したのは **publish の後・`vpk pack` の前**という位置と、
**逆にすると署名が壊れる**という理由だけ。

### 2. `CODE_SIGNING_POLICY.md` は「未定」と書くための文書になった

D-10 はファイルを要求している。中身は「署名していない」「予定は未定」
「代わりに出どころを辿れる」の 3 点。

**自己署名を使わない理由も書いた。** 書かないと、
「証明書を入れれば警告が消える」と思った人が同じ案に戻ってくる。

## 宿題

- 署名するかどうかを決める（**決める予定も未定**）
- 決めた場合、どの方式か（SignPath Foundation / 有料の証明書 / Azure Trusted Signing など）
- SmartScreen の警告が実際にどう出るか（**未検証**。インストーラーをまだ作っていない）

## 却下した案

| 案 | 却下の理由 |
|---|---|
| SignPath の記述をコメントのまま残す | **決めていないことが決まったように見える。** 後から読んだ人が「SignPath を使う方針だ」と受け取る（決定 1） |
| 署名の段そのものを消す | 入れる位置を忘れる。**`publish` の後・`vpk pack` の前**という順序は、間違えると署名が壊れる形で表れる（ADR-0031 決定 4 のこの部分は正しかった） |
| `CODE_SIGNING_POLICY.md` を作らない | **D-10 がファイルを要求している。** 署名しないこともひとつの方針で、書く価値がある（決定 2） |
| `CODE_SIGNING_POLICY.md` に「SignPath に申請予定」と書く | **嘘になる。** 申請するかどうかが未定（決定 2） |
| 自己署名証明書で署名する | SmartScreen の警告は消えない（評判が無いため）。**「署名されている」という誤った安心だけが残る**（決定 2） |
| 署名が無いことを README に書かない | 利用者は警告を見て「怪しいソフト」と判断する。**出ることが分かっていて黙らない**（決定 4） |
| 「承認されるまでは未署名」と書く | **承認されるかどうかが未定。** 近いうちに署名されるという誤った期待を与える（決定 4） |
| 署名をやめたので、手元ビルドでリリースしてもよいことにする | 出どころを辿れることは、**署名の有無と関係なく価値がある**（決定 3）。ADR-0031 決定 1 は守る |
