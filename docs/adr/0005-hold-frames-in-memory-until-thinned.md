# ADR-0005. 撮影中はフレームをメモリに保持し、間引いた後だけディスクに書く

- 状態: **実測・実機で確認**（2026-11-13 承認 / 同日に実測）
- 日付: 2026-11-13

## 背景

5.5 章（データ保持。見出しに「重要」と付いている）に次の 2 行がある。

> 一時データはメモリ上で済ませられる処理はメモリ上で行い、ディスクに書くのは Claude Code に渡す必要があるものに絞る

> 画像（frames/）… 一時データ。次のいずれかで**自動的に完全に消す**：結果画面を閉じたとき／次の撮影を始めたとき／アプリを終了したとき

素直に「撮ったら即ディスクへ書き、最後に要らないものを消す」と作ると、次が起きる。

- 撮影 60 秒・間隔 0.5 秒・重複除去後に 80 枚採用 → 80 枚書いて、間引きで 60 枚**消す**
- 消したファイルの中身は**削除後もディスク上に残る**（通常の削除はブロックを解放するだけ）。
  5.5 が「完全に消す」を求めている対象を、そもそも書かないで済ませられる
- 異常終了（プロセスキル、電源断）で残る一時データの量が、書いた枚数に比例して増える

F-06 の上限は 20 枚。**Claude Code に渡す必要があるのは、最終的に残る 20 枚だけ。**

## 決定

### 1. 撮影中は符号化後のバイト列をメモリ上の `List<EncodedFrame>` に積む

ディスクには一切書かない。`EncodedFrame` は JPEG バイト列・経過秒・ピクセル寸法を持つ `record`。

JPEG 1 枚は長辺 1280px（F-06）で概ね 150〜300 KB。200 枚で 30〜60 MB。
元の BGRA（4K で 1 枚 33 MB）を保持するのに比べて 2 桁小さい。

### 2. 撮影停止後に間引き、残った分だけを `frames/` へ書く

```
撮影中:  BGRA ─dHash判定─▶ 採用 ─縮小+JPEG─▶ メモリ（List<EncodedFrame>）
撮影停止: メモリ ─EvenTimeFrameThinner（上限20枚）─▶ ディスク（frames/）
```

書き出すファイル名は経過秒が読める形にする（F-07 / 2 章「撮影開始からの経過秒数」）。

```
frames/frame_001_t0000.0s.jpg
frames/frame_002_t0002.0s.jpg
```

### 3. メモリ上の保持枚数に上限（既定 200 枚）を設け、超えたらその場で間引く

撮影時間の上限は設定で広げられる（F-03 の既定は 60 秒）。
間隔 0.5 秒で 10 分撮れば受信 1200 枚になり、重複除去をすり抜ける割合によっては
メモリが数百 MB に届く。上限に達したら、その時点で `EvenTimeFrameThinner` を
`上限 / 2` の枚数で走らせて半分に落とす。

**この「その場の間引き」は時間的な均等性を少し崩す。**
後半のフレームが相対的に密になるが、最終的な間引きで再度均等化されるため影響は小さい。

### 4. ディスクへの書き出しと削除は `ISessionWorkspace` 1 箇所に閉じる

一時データを作る場所・消す場所を 1 クラスに集めることで、消し漏れを「このクラスを読めば分かる」状態にする。
削除は `Directory.Delete(path, recursive: true)`。
起動時は `%LOCALAPPDATA%\NutLens\work\` の**全子フォルダ**を消す（5.5「異常終了などで一時データが残った場合」）。

### 5. 「一時データを残す」デバッグ設定を既定オフで用意する

5.5 が明示的に許している。`KeepTemporaryData`（既定 `false`）。
**既定が false であることが目的の達成に必要**なので、設定画面では既定値を変えた状態を分かるように出す。

## 実装で分かったこと（2026-11-13）

### 1. JPEG 1 枚の実サイズ

| 入力 | 縮小後 | ファイルサイズ |
|---|---|---|
| デスクトップ全体（2560 × 1440、情報量が多い） | 1280 × 720 | **293 KB** |
| 単色が大半の窓（626 × 353） | 原寸（縮小不要） | 11〜13 KB |

見積もり（150〜300 KB）の上端に当たった。
**メモリ上限 200 枚で約 57 MB。** 見積もりどおりの規模で、上限 200 枚は妥当。
ただしデスクトップ全体は映画のフレームより情報量が多いので、これが最悪値に近い。

### 2. 「書かずに済ませる」が実際に効いている

確認ツールの実行で、撮影中は `frames/` が空のまま、
停止後に間引き済みの分だけが現れることを確認した。
受信 9 枚 → 書き出し 1 枚、受信 10 枚 → 書き出し 7 枚（しきい値 0 の場合）。
**捨てたフレームは一度もディスクに触れていない。**

## 影響

- 撮影を手動停止するまで `frames/` は空。UI で「採用 n 枚」を出さないと、
  利用者から見て何も起きていないように見える。進捗表示（`IProgress<CaptureProgress>`）が必須になる
- アプリが異常終了すると、その回の撮影結果は**全部失われる**（ディスクに無いので復旧できない）。
  一時データである以上これは仕様どおりだが、長時間の撮影を失う体験は良くない。
  段階 4 で「撮影時間の既定 60 秒」を超える指定をしたときの注意表示を検討する（宿題）
- 段階 3 の音声は WAV で数 MB〜数十 MB になり、Whisper に渡すためにディスクが必要。
  **音声はこの決定の対象外**（`audio.wav` は従来どおりディスクに書く）

## 宿題

- 長時間撮影時の注意表示をどこに出すか（段階 4 で決める）

### 片付いた宿題

- ~~メモリ上限 200 枚の妥当性~~ → 実測で JPEG 1 枚が最大 293 KB、200 枚で約 57 MB。妥当と判断

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 採用したフレームを即ディスクへ書き、最後に要らないものを消す | **消したファイルの中身はディスク上に残る。** 5.5 が「完全に消す」を求める対象を、書かずに済ませられるのに書いてしまう。加えて異常終了時の残骸が最大 10 倍（200 枚 vs 20 枚）になる |
| BGRA の生バイトのままメモリに持ち、停止後に間引いて符号化する | 4K で 1 枚 33 MB。200 枚で 6.6 GB。**撮影中に確保に失敗する** |
| 間引きを撮影中に逐次行い、常に 20 枚に保つ | 撮影が途中で止まる（手動停止）場合に「全体の時間範囲」が確定していないため、均等な間引きができない。前半だけ密なフレーム列になる |
| メモリ上限を設けず、無制限に積む | 撮影時間を設定で広げられる以上、上限が無ければ確保失敗が起きる。**落ちるのは長時間撮影の最後**で、その回の結果を全部失う |
| `MemoryMappedFile` / 一時ファイルに書いて読み戻す | ディスクに書く点で決定 1 の目的を達しない。暗号化もしないので「書かない」ことの代わりにならない |
| 削除に SDelete 相当の上書き削除を使う | 外部ツールの同梱かコピー処理の自作が必要で、SSD では TRIM / ウェアレベリングのため**上書きが実際に同じブロックに当たる保証が無い**。効果が保証されない処理を「完全に消す」と称するのは 3 章（検証の度合いを偽らない）に反する。**書かないことが唯一確実な手段** |
