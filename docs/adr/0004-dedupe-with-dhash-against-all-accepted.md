# ADR-0004. 重複判定を dHash で行い、受理済みフレーム全件と比較する

- 状態: **実測・実機で確認**（2026-11-13 承認 / 同日に実測。**ただし既定しきい値の妥当性は未確定**）
- 日付: 2026-11-13

## 背景

F-05 は「知覚ハッシュ（dHash など）でほぼ同じフレームを除く。しきい値は設定で変えられる」。
2 章の前提には、より重要な一文がある。

> ショート動画はループ再生されるため、同じ場面が繰り返し撮れることを前提に重複を除く

つまり除きたい重複は 2 種類ある。

| 種類 | 例（撮影間隔 2 秒・動画長 15 秒の場合） |
|---|---|
| 連続する重複 | 静止したカットを 2 秒間隔で 3 回撮る → 隣り合うフレームが似る |
| **周期的な重複** | 15 秒でループ → t=1s と t=16s が同じ場面。**間に 7 枚の別の場面が挟まる** |

「直前のフレームと比べる」実装では後者が一切落ちない。
ループが 2 周すれば採用枚数は約 2 倍、3 周すれば約 3 倍になり、
F-06 の上限 20 枚の枠を同じ場面の重複で埋めてしまう。

## 決定

### 1. dHash（64 bit）を使う

BGRA の生バイトから、次の手順で 64 bit を作る。

```
1. 9 × 8 のグレースケールへ縮小（ボックス平均：元画像を 9×8 の格子に分け、各区画の平均輝度）
   輝度 = (R * 299 + G * 587 + B * 114) / 1000
2. 各行で横に隣り合う 2 つを比べ、左 > 右 なら 1、そうでなければ 0
   → 8 行 × 8 比較 = 64 bit
```

縮小に**ボックス平均（区画内の全画素の平均）を使い、最近傍の間引きは使わない。**
最近傍だと、動画の圧縮ノイズを拾った 1 画素でビットが反転し、同じ場面でもハッシュが安定しない。

距離はハミング距離（`BitOperations.PopCount(a ^ b)`）。

### 2. 受理済みフレーム**全件**と比較する

新しいフレームのハッシュを、それまでに採用したすべてのフレームのハッシュと比べ、
**最小距離 ≤ しきい値なら棄却**する。

```csharp
// 擬似コード
bool TryAccept(ulong hash)
{
    foreach (ulong accepted in this.acceptedHashes)
    {
        if (DHash.Hamming(hash, accepted) <= this.threshold) { return false; }
    }
    this.acceptedHashes.Add(hash);
    return true;
}
```

採用枚数の上限はメモリ側で 200 枚（ADR-0005）、最終的に 20 枚（F-06）なので、
全件比較は最大 200 回の `PopCount`。1 フレームあたり 1 マイクロ秒に届かない規模で、
O(n²) を避ける工夫（BK-tree 等）は要らない。

### 3. しきい値の既定値を 5 にする

64 bit のうち 5 bit 以内の違いを「同じ場面」とみなす。設定で 0〜16 の範囲で変えられる（F-05）。

- 0 … 完全一致のみ棄却
- 5 … 既定。圧縮ノイズと数フレーム分の微動を吸収する想定
- 10 以上 … 別カットでも構図が似ていると落ちやすい

**この既定値は一般的に使われる値からの推測であり、実測していない。** 宿題に落とす。

### 4. ハッシュの計算は符号化より先に行う

縮小・JPEG 符号化（F-06）は重い。棄却されるフレームに符号化コストを払わないよう、
`CapturedFrame`（BGRA 生バイト）の段階でハッシュを計算して判定し、通ったものだけを符号化する。

```
BGRA → dHash → 棄却？ ─yes─▶ 捨てる（符号化しない）
                  └─no──▶ 縮小 + JPEG → メモリに保持
```

### 5. 実装を `NutLens.Core` に置く

BGRA のバイト列と幅・高さ・ストライドだけで計算でき、Windows 依存が無い（ADR-0002 決定 2）。
`DHash` は純粋関数の `static` メソッド、状態を持つ `DHashDuplicateFrameFilter` はインスタンス。

## 実装で分かったこと（2026-11-13）

### 1. 平坦な絵では別の場面でも距離が 1〜4 にしかならない

確認ツール（`tools/NutLens.CaptureProbe --animate`）で、
**1 秒ごとに背景色と中央の数字が変わる窓**を 12 秒間・間隔 1 秒で撮り、
保存した JPEG から dHash を計算し直した実測値（しきい値 0 で全件採用させた）:

```
frame_001  dHash=0x8088B0B094808080  前フレーム群との最小距離 = -
frame_002  dHash=0x8080909090808080  最小距離 = 4
frame_003  dHash=0x8080B09090808080  最小距離 = 1
frame_004  dHash=0x80889090B0808080  最小距離 = 2
frame_005  dHash=0x808090B090808080  最小距離 = 1
frame_006  dHash=0x8080B0B0B0808080  最小距離 = 2
frame_007  dHash=0x8084B0A0B0848080  最小距離 = 3
```

**しきい値 5（既定）では、この 7 枚はすべて「同じ場面」と判定されて 1 枚しか残らない。**
実際、同じ条件をしきい値 5 で走らせると採用は 1 枚だった。

理由は 2 つある。

- **dHash は色を見ない。** 輝度だけを使うので、背景色が赤→緑→青と変わっても距離は動かない
- **平坦な面は区画の平均が揃い、ビットが立たない。** 画面の大半が単色だと、
  構造を持つのはタイトルバーと中央の数字だけになり、動く部分が格子 9 × 8 のうち数区画に留まる

### 2. これが本番の入力にも当てはまるかは、まだ分からない

上の映像は**dHash にとって最悪に近い合成映像**（巨大な単色面＋小さなグリフ）で、
写真的な映像が大半を占める実際のフリップ動画とは性質が違う。
**既定値 5 が実際のフリップ動画で妥当かどうかは、依然として未検証。** 宿題に残す。

ただし、フリップ動画には黒帯・単色のタイトルカード・字幕だけが変わるカットも実在するので、
**この弱点は現実にも起こりうる**と考えておく。

### 3. 実物のフリップ動画で測った（2026-11-13、利用者が撮影）

YouTube Shorts の映画紹介動画を**ブラウザの窓ごと**、2 秒間隔で 30 秒撮影（14 枚採用）。
保存された 1280 × 720 の JPEG から測り直した。

**フレーム全体（＝撮ったまま）:**

```
frame_001  dHash=0x7659595171711569  最小距離 = -
frame_002  dHash=0x7669696171711769  最小距離 = 7
frame_003  dHash=0x7649797161311769  最小距離 = 5
frame_004  dHash=0x7671616171311769  最小距離 = 4
frame_005  dHash=0x7661617131311769  最小距離 = 3
frame_007  dHash=0x7661617171391769  最小距離 = 2   ← 最も近い組
…
```

**しきい値を変えたときに残る枚数:**

| しきい値 | フレーム全体 | 動画の部分だけ切り出し |
|---|---|---|
| 0〜1 | 14 / 14 | 14 / 14 |
| 2 | 12 / 14 | 14 / 14 |
| 3 | 10 / 14 | 14 / 14 |
| **5（既定）** | **6 / 14** | **14 / 14** |
| 7 | 4 / 14 | 13 / 14 |

**既定のしきい値 5 では、14 の別々の場面が 6 枚に潰れる。**

### 4. 原因は「動かない部分が画面の大半を占めること」

撮影されたフレームの内訳:

| 部分 | 画面に占める割合 | 変化 |
|---|---|---|
| ブラウザのタブ・ブックマーク・サイドバー | 幅の約 70% | **動かない** |
| フリップ動画の上部の固定テロップ（作品の惹句） | 動画領域の約 25% | **動かない** |
| フリップ動画の下部（`©TAXi3 (2003)` と背景イラスト） | 動画領域の約 25% | **動かない** |
| 実際に動く映像 | **画面全体の 1 割程度** | 変わる |

ハッシュ値にもそのまま現れている。全フレームで上位が `0x76…`、下位が `…1769` で共通
（＝固定部分）、変わるのは中ほどだけ。
9 × 8 の格子のうち、動く部分に割り当たるマス目が数個しかない。

**フリップ動画は作りからして固定部分が大きい。**
これは「この動画がたまたまそうだった」のではなく、形式に由来する。

### 5. 縮小ではハッシュはほぼ動かない（測定の妥当性）

撮影時の重複判定は原寸の BGRA に、保存されるのは縮小後の JPEG に対して行われる。
両者が食い違うなら上の測定は意味を持たないので、確かめた。

| 縮小 | 原寸ハッシュとのずれ |
|---|---|
| 1/2 | 中央値 1 / 最大 1 |
| 1/4 | 0〜1 |
| 1/8 | 3〜4 |

**保存後のフレームで測った距離は、撮影時に効いた距離と同じものとして読んでよい。**

### 6. 格子を細かくすると分離が広がる

| 格子 | bit 数 | 別の場面どうしの最小距離 | 縮小によるずれ（ノイズ） | 分離比 |
|---|---|---|---|---|
| **9 × 8（現行）** | 64 | **2** | 1 | 2.0 |
| 13 × 12 | 144 | 5 | 4 | 1.3 |
| 17 × 16 | 256 | 9 | 4 | 2.3 |
| 25 × 24 | 576 | **23** | 5 | **4.6** |

現行の 64 bit では、**置けるしきい値が実質 1 しかない**（ノイズ 1、信号 2）。
25 × 24 なら 5〜23 の間に置ける。

この扱いは ADR-0015 で決める。

### 7. しきい値を測れる手段を残した

`tools/NutLens.CaptureProbe` に測るための入口がある。しきい値を決め直すときは、推測ではなくこれで測る。

```powershell
# 保存済みフレームの dHash・総当たりの距離・しきい値ごとの採用枚数
dotnet run --project tools/NutLens.CaptureProbe -- --hashes "<frames フォルダ>"

# 動画の部分だけを切り出して同じことを測る（引数は X Y 幅 高さ）
dotnet run --project tools/NutLens.CaptureProbe -- 492 92 344 620 --hashes "<frames フォルダ>"

# 縮小でハッシュがどれだけ動くか（測定の妥当性の確認）
dotnet run --project tools/NutLens.CaptureProbe -- --scale-sensitivity "<frames フォルダ>"

# 格子の細かさを変えたときの分離具合
dotnet run --project tools/NutLens.CaptureProbe -- --grid "<frames フォルダ>"
```

## 影響

- `IDuplicateFrameFilter` は状態（受理済みハッシュ）を持つので、**1 回の撮影ごとに作り直す**。
  使い回すと前回の撮影のハッシュが残り、別の動画のフレームが落ちる
- ループ 1 周分を超えて撮影しても、採用枚数は場面の種類数で飽和する。
  撮影時間を長くしても枚数が増えなくなるのは**正しい挙動**だが、UI では
  「採用 n 枚」だけでなく「受信 m 枚」も出して、動いていることが分かるようにする

## ループ再生での実測（2026-11-14。ADR-0015 実装で分かったこと 3）

この決定の前提である「ループ再生で戻ってきた同じ場面を落とせること」を実物で測った。

**落とせるのは一部だけだった。**

| ループで戻ってきた組（時刻差 114.4 秒） | 距離 | しきい値 12 で落ちるか |
|---|---|---|
| frame_006 ↔ frame_063 | 3 | 落ちる |
| frame_003 ↔ frame_060 | 11 | 落ちる |
| frame_007 ↔ frame_064 | 11 | 落ちる |
| frame_008 ↔ frame_065 | **19** | **落ちない** |

**撮影間隔（2 秒）とループ周期（114.4 秒）が同期していない**ため、
2 周目のフレームは 1 周目と少しずれた瞬間に当たる。
動きの速いショットでは、そのずれが 19 ビットの差になる。

そして**別の場面どうしも 15〜19 の帯にいる**ため、しきい値を上げて取りこぼしを拾うと、
別の場面を失う。

**この決定（受理済み全件と比較する）は正しいが、万能ではない。**
ループの重複を完全には除けないことを仕様として受け入れ、
残った重複は枚数の間引き（F-06、上限 20 枚）で吸収する。

## 宿題

- **色を見ないことへの対処（未了）。** 輝度が同じで色だけ違うカットは原理的に区別できない。
  必要なら「色のヒストグラムの差」を補助条件として足す
- 測定は動画 1 本のみ。別の作りのフリップ動画では測っていない

### 片付いた宿題

- ~~しきい値 5 が実際のフリップ動画で妥当か~~ → **妥当でない。**
  ブラウザの窓ごと撮ると 14 場面が 6 枚に潰れる（実装で分かったこと 3）。
  原因は動かない部分が画面の大半を占めること（同 4）
- ~~ボックス平均縮小の端数処理~~ → テストで固定
- ~~保存後のフレームで測った距離が撮影時と同じか~~ → 同じ。縮小によるずれは 1 以下（同 5）

### 片付いた宿題

- ~~ボックス平均縮小の端数処理~~ → `DHashTests.格子より小さい画像でも例外にならない`
  （1×1 / 4×3 / 9×8 / 8×9）と `指定したビット列どおりのハッシュになる` で固定済み

## 却下した案

| 案 | 却下の理由 |
|---|---|
| **直前のフレームとだけ比較する** | ループ再生の周期的な重複が一切落ちない（決定 2 の背景）。採用枚数がループ周回数に比例して増え、**上限 20 枚の枠を同じ場面で埋める** |
| 直近 N 枚（N=5 程度）と比較する | ループ周期が「N × 撮影間隔」より長いと落ちない。動画長は 15〜60 秒、撮影間隔は 0.5〜10 秒と幅があり、**N をいくつにしても落ちない組み合わせが残る** |
| aHash（平均ハッシュ） | 全体の明るさが変わるだけでハッシュが大きく動く。フェードイン・フェードアウトの多いフリップ動画で、同じ場面が別物として残る |
| pHash（DCT ベース） | 回転・拡大縮小に強いが、今回の入力は同じ動画の同じ解像度のフレームで、その強さは要らない。64 点の DCT を自前実装するか依存を足すことになり、dHash に対する利得がコストに見合わない |
| SSIM や画素差分の平均 | 全画素を保持して比較することになり、ADR-0005 の「メモリに持つのは符号化後だけ」と噛み合わない。計算量も 2 桁以上大きい |
| ハッシュを JPEG 符号化後の画像から計算する | 棄却するフレームにも符号化コストを払う（決定 4 の逆）。JPEG の量子化でノイズが増え、安定性も下がる |
| 距離の計算に BK-tree / LSH を使う | 比較対象が最大 200 件。**最適化の必要が無いところに構造を足すと、端のケースのバグだけが増える** |
