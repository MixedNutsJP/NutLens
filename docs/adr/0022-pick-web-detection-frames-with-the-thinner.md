# ADR-0022. 送るフレームを既存の間引き器で選び、結果も失敗も `web_detection.json` 1 つに残す

- 状態: **採用**（2026-11-14 承認）
- 日付: 2026-11-14

## 背景

5.6 のうち、呼び方（ADR-0019）・鍵の置き場（ADR-0020）・有効化の筋道（ADR-0021）を
決めたあとに残るのは、**運用の 4 点**。

> - 送るフレームは、重複除去の後のフレームから**代表的なもの**を選び、1 回の解析あたりの上限枚数（初期値 3 枚）を設定で決められるようにする
> - 結果を `web_detection.json` として一時作業フォルダに置き、プロンプトに「参考情報（外部の画像検索の結果。誤りを含む可能性がある）」として入れる
> - 実行するたびに、結果画面に「Web Detection を使用（n 枚送信）」と表示する
> - 通信エラー・認証エラー・利用上限エラーのときは、Web Detection なしで解析を続け、その旨を表示する

決めるべきことは 4 つ。

1. 「代表的なもの」をどう選ぶか
2. いつ走らせるか
3. `web_detection.json` に何を書くか
4. 「n 枚送信」と「失敗した旨」を、**撮影画面から結果画面までどう運ぶか**

4 が効いてくる。画面は 撮影 → プロンプト確認 → 進捗 → 結果 の 4 つを跨ぐ。

## 決定

### 1. 代表フレームは `EvenTimeFrameThinner` で選ぶ。新しい選び方を作らない

`frames/` に残っているフレーム（＝重複除去と間引きが済んだもの。F-05 / F-06）を、
**さらに時間軸で均等に `MaxImages` 枚へ絞る。**

```csharp
IReadOnlyList<FrameReference> selected = thinner.Thin(frames, settings.WebDetection.MaxImages);
```

`EvenTimeFrameThinner` は `ITimestamped` に対する汎用で、最初と最後が必ず残り、
既にテストがある（ADR-0004 / F-06）。
**「代表的」を新しく定義すると、そのしきい値をまた実測することになる。**
測っていない値で挙動を変えない。

| 設定 | 値 |
|---|---|
| `WebDetection.MaxImages` | 既定 **3**（5.6 の初期値）。範囲 1〜10 |

### 2. 走らせるのは OCR の後、プロンプト確認の前。1 回だけ

```
撮影 → 文字起こし → OCR → Web Detection → プロンプト確認 → claude → 結果
      └──────── MediaProcessingService ────┘ └ WebDetectionService ┘
```

`MediaProcessingService` の中には入れない。
あれは「文字起こしと OCR を行う役」で、**網の外に出る処理を混ぜると、
どのクラスが通信するのかが読めなくなる。** 別の `WebDetectionService` にする。

呼ぶのは `CaptureViewModel.ProcessMediaAsync` の後段（撮影の直後）。
**プロンプト確認画面からは呼ばない。** あの画面はメモを打つたびに
`Rebuild()` でプロンプトを作り直すので、**打鍵のたびに課金される。**

### 3. `web_detection.json` の書式はこちらで決める

Google の応答をそのまま書かない。載せるのは 5.6 が挙げた 3 つと、送った枚数・フレーム名。

```json
{
  "status": "ok",
  "sentImageCount": 3,
  "frames": [
    {
      "file": "frames/frame_001_t0000.0s.jpg",
      "elapsedSeconds": 0.0,
      "bestGuessLabels": ["movie scene"],
      "webEntities": [ { "description": "…", "score": 0.72 } ],
      "pagesWithMatchingImages": [ { "title": "…", "url": "https://…" } ]
    }
  ]
}
```

`status` は `ok` / `network` / `auth` / `quota` / `invalid` のいずれか。
失敗のときは `frames` が空で、`message` に短い説明が入る。

**要求の中身（base64 の画像、端点の URL）は書かない。**
URL にはクエリ文字列として API キーが入っている（ADR-0020 決定 4）。

### 4. 成功も失敗も、同じ 1 ファイルに残す

決定 3 の `status` が、そのまま「結果画面に何を出すか」になる。

| `status` | 結果画面 |
|---|---|
| ファイルが無い | 何も出さない（使っていない） |
| `ok` | 「Web Detection を使用（n 枚送信）」 |
| `network` / `auth` / `quota` / `invalid` | 「Web Detection は使えませんでした（理由）。解析は続けました」 |

**画面から画面へ引き回さない。** 状態の置き場はもう一時フォルダにある。
4 つの画面に引数を足して運ぶと、増えるのは引数だけで、
`web_detection.json` との食い違いという新しい不具合の口が開く。

`web_detection.json` は一時データなので、ほかと一緒に消える（5.5）。
**「n 枚送った」という事実が残り続けないことは、5.5 の趣旨に合う。**

### 5. 失敗は種類を分けて文にする。解析は止めない

| 起きたこと | `status` | 画面に出す |
|---|---|---|
| 名前解決・接続できない、タイムアウト | `network` | ネットワークに繋がりませんでした |
| HTTP 401 / 403 | `auth` | API キーが拒否されました。キーと Vision API の有効化をご確認ください |
| HTTP 429、`RESOURCE_EXHAUSTED` | `quota` | 利用上限に達しました |
| HTTP 400、応答が読めない | `invalid` | 応答を読み取れませんでした |

いずれも**例外を外に投げない。** 補助情報が取れなかっただけで解析を止めない
（概要設計 §10.1。文字起こしと OCR と同じ扱い）。

HTTP の例外は、こちらで作った短い文に**必ず置き換えてから**外へ出す（ADR-0020 決定 4）。

### 6. プロンプトに差し込むのは `status` が `ok` のときだけ

`AnalysisService.PreparePrompt` は今も `web_detection.json` を読んで
`{{web_detection}}` に差し込んでいる。ここに型付きの読み役を挟む。

```csharp
// status が ok 以外なら null を返す（= プロンプトには「使っていません」が入る）
string? reference = WebDetectionDocument.TryReadReference(layout.WebDetectionFile);
```

**`PromptComposer` は置換だけの役のまま変えない。**
あれに JSON の解釈を足すと、テンプレートの不具合と応答の不具合が同じ場所で起きる。

### 7. タイムアウトは 30 秒。撮影直後の待ちを無限にしない

3 枚を 1 往復（ADR-0019 決定 3）なので、応答までの時間は 1 回分。
30 秒を超えたら `network` として打ち切る。
**撮影が終わったのに画面が進まない状態を作らない。**

## 影響

- `FrameReference` に `ITimestamped` を実装させる（`Elapsed` は既にある）。
  間引き器を使い回すため
- `WebDetectionSettings` が増える：`Enabled`（既定 false）/ `ConsentVersion`（既定 0）/
  `MaxImages`（既定 3）/ `TimeoutSeconds`（既定 30）。**API キーは入らない**（ADR-0020）
- `CaptureViewModel` の撮影後の流れに 1 段増える
- `ResultViewModel` が `web_detection.json` を読む
- analyzer 側の `CLAUDE.md` に「`status` が `ok` 以外なら参考情報は無いものとして扱う」を足す。
  「参考情報は手がかりの一つにすぎず、ほかの手がかりとの照合なしに結論にしない」は**既に書いてある**

## 実装で分かったこと（2026-11-14）

### 1. `FrameReference` に `ITimestamped` を足すだけで間引き器が使えた

間引き器は `IReadOnlyList<T> Thin<T>(…) where T : ITimestamped` という汎用。
`FrameReference` には既に `Elapsed` があったので、インタフェースの宣言を 1 行足すだけで済んだ。
**新しい選び方を書かずに済んでいる。**

テストで確かめたこと（いずれも成功）:

| 確かめたこと | 結果 |
|---|---|
| 10 枚から 3 枚に絞る | 3 枚 |
| 最初（2.0 秒）と最後（20.0 秒）が必ず入る | 入る |
| 枚数が上限以下ならそのまま | 2 枚なら 2 枚 |

### 2. 失敗した回の `web_detection.json` がプロンプトに漏れないことを固定した

`AnalysisServiceTests` に 1 件足した。
`status` が `auth` のファイルを置いてプロンプトを作ると、
**エラーの文面がプロンプトに現れない。** `ok` に書き換えると現れる。

### 3. 確認用の口を 2 つ作った

```powershell
# 3 条件の揃い具合を見る（通信しない・課金されない）
dotnet run --project tools/NutLens.CaptureProbe -- --env

# 保存済みのフレームで実際に送る（**課金される**。既定 3 枚＝3 ユニット）
dotnet run --project tools/NutLens.CaptureProbe -- --web-detect "<frames>"
```

後者は**アプリと同じ選び方（決定 1）を使う。**
別の選び方で確かめると、本番の挙動を確かめたことにならない。

## 宿題

- **1 度も呼んでいない。** `status` の切り分け（特に `quota` が 429 で来るのか
  200＋`error` で来るのか）は ADR-0019 の宿題と同じ根を持つ
- `MaxImages` の既定 3 が妥当かは測っていない。5.6 の初期値をそのまま使っている
- 30 秒という上限に根拠は無い。実際の応答時間を見て決め直す
- 撮影の直後に走らせると、**利用者が「解析しない」を選んだ場合でも課金済み**になる。
  プロンプト確認画面で「送る」を押した後に動かすほうが無駄が無いが、
  そうすると画面が 1 つ増える。段階 4 で見直す

## 却下した案

| 案 | 却下の理由 |
|---|---|
| ハッシュの距離が遠い順に選ぶなど、専用の代表フレーム選びを作る | 選び方がもう 1 つ増え、そのしきい値をまた実測することになる。**間引き器は既にテストがある**（決定 1） |
| 残ったフレームをすべて送る | 20 枚なら課金が約 7 倍。5.6 は上限 3 枚を初期値にしている |
| プロンプト確認画面で呼ぶ | あの画面はメモを打つたびに `Rebuild()` が走る。**打鍵のたびに課金される**（決定 2） |
| `MediaProcessingService` の 3 段目にする | 「文字起こしと OCR をする役」に通信が混ざり、**どのクラスが外へ出るのかが読めなくなる**（決定 2・D-08） |
| Google の応答をそのまま `web_detection.json` に書く | 使わない画像 URL が数十件並ぶ。プロンプトが膨らみ、Claude の利用枠を残骸で消費する（ADR-0019 決定 5） |
| 結果を画面から画面へ引数で運ぶ | 4 つの画面に引数が増える。状態の置き場はもう一時フォルダにあり、**二重になった分だけ食い違う**（決定 4） |
| 失敗したときは何も残さない | 結果画面が「使っていない」と「試したが失敗した」を区別できない。**5.6 は後者を表示せよと言っている**（決定 4） |
| 失敗を例外で上へ投げる | 補助情報が取れなかっただけで解析が止まる。文字起こし・OCR と扱いが揃わない（決定 5） |
| `PromptComposer` に `status` の判定を足す | 置換だけの役に JSON の解釈が混ざる。テンプレートの不具合と応答の不具合が同じ場所で起きる（決定 6） |
| タイムアウトを設けない | 撮影が終わったのに画面が進まない状態ができる（決定 7） |
