# ADR-0039. `0.x` と接尾辞つきの版は prerelease として出し、更新確認も同じ規則で探す

- 状態: **採用**（2026-11-14。利用者が選択）
- 日付: 2026-11-14
- 補う対象: [ADR-0031](0031-release-from-tags-and-leave-a-slot-for-signing.md)（**決定は覆さない**）

## 背景

v0.1.0 を初めて出したとき、**通常のリリースとして公開された。**

```
tagName: v0.1.0
isDraft: false
isPrerelease: false     ← ここ
```

`release.yml` が `prerelease` を指定していないので、`action-gh-release` の既定
（`false`）がそのまま効いた。

これが実態と合わない。この版で**確かめていないもの**は、たとえば次のとおり。

| 機能 | 状態 |
|---|---|
| Web Detection | **実 API を一度も呼んでいない** |
| 自動更新 | **一度も適用していない**（次の版が出るまで試せない） |
| 文字起こし | `base` 以外のモデルで動かしていない |
| トレイ・ホットキーの押下・保存先の移動 | **未目視** |
| SmartScreen の出方 | **未確認** |

`README.md` の「動作確認の範囲」と各 ADR の状態欄には書いてある。
**しかし Releases の一覧では、通常のリリースとして並ぶ。**

このリポジトリは「**確かめていないことを『動く』と書かない**」を
一番強い作法に置いている（`CONTRIBUTING.md` §5）。
**リリースの見え方だけがそこから外れていた。**

手で `gh release edit --prerelease` を叩けば直る。
**だから危ない。** 次の版で忘れる。

## 決定

### 1. 版の文字列から **prerelease かどうかを機械的に決める**

```bash
case "$value" in
  *-*) prerelease=true ;;   # 1.0.0-rc.1 / 0.1.0-test など、接尾辞つき
  0.*) prerelease=true ;;   # 0.x は安定版ではない
  *)   prerelease=false ;;  # 1.0.0 以降の、接尾辞なし
esac
```

**順序を変えない。** 接尾辞の判定を先に置く。
後にすると `1.0.0-rc.1` が「`0.` で始まらない」ので通常のリリースになる。

| 版 | prerelease | なぜ |
|---|---|---|
| `0.1.0` | **true** | **`0.x` は安定版ではない。** SemVer がそう決めている |
| `0.9.5` | **true** | 同じ |
| `1.0.0-rc.1` | **true** | 接尾辞がある |
| `1.0.0` | false | ここで初めて通常のリリースになる |
| `10.2.0` | false | `0.` で始まらない（`10.` と `0.` を混同しない） |

### 2. 判定は**ワークフローの中**に置く。人が選ばない

`release.yml` の「版を決める」段で `prerelease` も一緒に出し、
`action-gh-release` に渡す。

```yaml
prerelease: ${{ steps.version.outputs.prerelease }}
```

**タグを打つ人が毎回考える形にしない。** 考える形にすると、
急いでいるときに間違う。`v1.0.0` を打った瞬間に、初めて通常のリリースになる。

### 3. **更新確認も prerelease を探す。** 同じ判定を使う

**決定 1 だけ入れると、自動更新が壊れる。**

```csharp
new GithubSource(RepositoryUrl(), null, false)
//                                      ^^^^^ prerelease
```

Velopack の `GithubSource` の `prerelease` 引数は、こう書かれている。

> If true, pre-releases will be also be searched / downloaded.
> **If false, only stable releases will be considered.**

`0.x` を全部 prerelease として出すと、**探す対象が 0 件になる。**
しかも**失敗しない。** 「最新です」と静かに返り続けるので、
**更新が来ていないのか、見ていないのかが区別できない。**

いま動いている版に合わせて決める。

| 動いている版 | 探す対象 | なぜ |
|---|---|---|
| `0.1.0`（prerelease） | **prerelease も** | **これしか存在しない** |
| `1.0.0-rc.1` | prerelease も | rc を使っている人は rc を追いたい |
| `1.0.0`（安定版） | **安定版だけ** | **安定版の利用者に rc を出さない** |
| 読み取れない | prerelease も | 取りこぼす（更新に気づけない）ほうが困る |

**判定はワークフロー側（決定 1）と同じ規則**にする。
`VelopackUpdateService.IsUnstable` と `release.yml` の `case` が同じことを言う。
**片方だけ変えると、出す側と探す側が食い違う。**

> **決定 1 とこの決定を別の ADR に分けない。**
> **片方だけ変えると壊れる**（prerelease で出して安定版だけ探す、
> あるいはその逆）。同じ場所に置いて、必ず一緒に読まれるようにする。

### 4. `1.0.0` を出す条件は**ここでは決めない**

「何が確かめられたら 1.0.0 か」は、まだ決められる段階にない。
`docs/adr/README.md` の「未処理の宿題」が目に見えて減ってから起こす。

**ここで決めるのは「0.x の間は prerelease」だけ。**

## 影響

- `release.yml` の「版を決める」段が `prerelease` も出すようになる
- `Release` の段に `prerelease:` が 1 行増える
- **`VelopackUpdateService` が `GithubSource` に `prerelease: true` を渡すようになる**
  （`0.x` で動いている間。決定 3）。`IsUnstable` / `SearchesPrereleases` が増える
- **v0.1.0 は手で印を付け直した**（`gh release edit v0.1.0 --prerelease`）。
  ワークフローの変更は次の版から効く
- Releases の一覧で「Pre-release」の札が付く。
  **`Latest` の札が付かなくなる**ので、入れ方の案内は README に頼る形が続く

## 実装で分かったこと（2026-11-14）

### 分岐は手元で確かめた（8 ケース）

```
0.1.0          -> prerelease=true
0.9.5          -> prerelease=true
0.1.0-test     -> prerelease=true
1.0.0-rc.1     -> prerelease=true     ← 順序が効いている
1.0.0          -> prerelease=false
10.2.0         -> prerelease=false    ← 0. と 10. を混同しない
2.3.4          -> prerelease=false
1.0.0-alpha    -> prerelease=true
```

**決定 1 の表と一致した。** ただしこれは `case` の分岐を同じ shell で回しただけで、
**ワークフローとして通したわけではない**（宿題に残す）。

### 2. 決定 1 だけを入れると、自動更新が静かに死ぬ

`VelopackUpdateService` は `GithubSource(..., false)` を渡していた。
**これを直さずに `0.x` を prerelease にすると、更新が一度も見つからない。**

見つからないことは**失敗として扱われない**（`UpdateCheckStatus.UpToDate` で返る）。
`CheckAsync` は例外も出さない。**「更新が無い」と「更新を見ていない」が同じ見え方になる。**

**リリースの見え方を変える決定が、更新の仕組みを壊す**という形だった。
決定 3 を同じ ADR に入れたのはこのため。

## 宿題

- **次の版を出すまで、この規則が効いていることを確かめられない。**
  `case` の分岐は手元で確かめられるが、**ワークフローで通したわけではない**
- **prerelease を実際に見つけて更新したことがない**（決定 3）。
  `0.1.0` → `0.1.1` を出して初めて確かめられる
- `1.0.0` を出す条件（決定 4 のとおり、意図して決めていない）

## 却下した案

| 案 | 却下の理由 |
|---|---|
| そのまま（通常のリリースとして出す） | **確かめていないものが「動く」ように見える。** このリポジトリで一番強い作法（`CONTRIBUTING.md` §5）から、リリースの見え方だけが外れる |
| 毎回手で `gh release edit --prerelease` を叩く | **忘れる。** 忘れたことに気づく仕組みが無い。1 行の自動化で消える手間を人に残さない |
| `workflow_dispatch` の入力で選ばせる | **タグ駆動なので入力が無い**（ADR-0031 決定 2）。入力を足すと、引き金が 2 つになる |
| タグの名前で区別する（`v0.1.0-pre` のように） | **版の文字列が汚れる。** Velopack と Inno に渡る版がそのまま変わり、`NutLensApp-0.1.0-pre-full.nupkg` のような名前になる |
| draft で出して、確認してから publish する | **自動更新が draft を見ない。** Velopack は Releases の公開済みのものを読むので、draft のままでは更新の経路が成立しない |
| `0.x` も通常のリリースにし、接尾辞だけで判定する | **`0.1.0` が「安定版」として並ぶ。** SemVer は `0.x` を「いつ壊れてもよい版」と定めている |
| `GithubSource` の `prerelease` を `false` のまま残す | **更新が一度も見つからない。** しかも失敗しないので、「最新です」と静かに返り続ける（決定 3） |
| `GithubSource` の `prerelease` を `true` に固定する | `0.x` の間は正しいが、**`1.0.0` を出した後も rc を安定版の利用者に出してしまう。** いま動いている版に合わせれば自動で切り替わる（決定 3） |
| 更新確認の対象を設定で選ばせる | **選べる形にすると「見ていない」状態を利用者が作れる。** 更新は既定で届くべきもの（ADR-0028） |
| 接尾辞の判定を後に置く | **`1.0.0-rc.1` が通常のリリースになる**（`0.` で始まらないため）。決定 1 の順序はこれを避けるため |
