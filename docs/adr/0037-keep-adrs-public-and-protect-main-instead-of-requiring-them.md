# ADR-0037. ADR は公開のまま維持者が書き、整合は `main` の保護で担保する

- 状態: **実測・実機で確認**（2026-11-14。利用者が選択）
- 日付: 2026-11-14
- 関わる文書: `CONTRIBUTING.md` / `.github/pull_request_template.md` / `docs/adr/README.md`

## 背景

公開の直前に、利用者から問いがあった。

> adr は私の個人的なものなのでignore除外が適切と思いますが、どうでしょうか

理由を聞いたところ、懸念は「個人情報」ではなく**寄稿の重さ**だった。

> 単純が AI コーディングのために作成しているので、パブリックである以上
> 第三者からの PR に ADR を要求するのは重いと感じたからです。
> かといって ADR を任意にすると実装とドキュメントが整合しなくなるんですよね

**この 2 つは両立しない、ように見える。**

| 立てたい方 | 犠牲になる方 |
|---|---|
| ADR を必須にする | 誤字 1 文字の PR にも ADR を求めることになり、**誰も PR を出さない** |
| ADR を任意にする | 決定と実装がずれていき、**ADR が「昔そう決めた」だけの死文になる** |

### ADR を `.gitignore` に入れて確かめたこと

まず「外す」案を実際に調べた。

| 調べたこと | 結果 |
|---|---|
| 個人情報が入っているか | **1 行だけ。** `docs/adr/README.md:7` に維持者のローカルパス（`C:\Users\…`）。この ADR の作業で消した |
| 非公開リポジトリへの言及 | **2 箇所。** ADR-0035 と `scripts/build-installer.ps1` が維持者の別プロジェクト名を出していた。同じ作業で一般化した |
| 外したときに壊れるもの | **`README.md` / `CONTRIBUTING.md` / `SECURITY.md` / `CODE_SIGNING_POLICY.md` / `docs/design/*` / `.github/workflows/ci.yml` が `docs/adr/` を指している。** 全部リンク切れになる |
| `ci.yml` の検査 | 「全 ADR が索引に載っているか」を見ている。**ADR が無くなると、この検査が常に失敗する** |

**外して困るものばかりで、外して守れるものは 1 行しか無かった。**
その 1 行は消せば済む。**よって「外す」は採らない。**

### 本当の問題は置き場ではなく、**誰に求めるか**だった

`CONTRIBUTING.md` は当初こう書いていた。

> **`CLAUDE.md` は変更の前に必ず読んでください。** 守られていない変更は取り込めません。
> ### 4. アーキテクチャ上の決定なら、先に ADR を出すこと
> **実装してから ADR を書かないでください。**

`CLAUDE.md` は**維持者が自分に課した作法**で、
もともと寄稿者に向けて書いたものではない。
それを寄稿の条件として掲げていたのが、重さの正体だった。

## 決定

### 1. ADR は**公開リポジトリに置いたままにする**

`.gitignore` に入れない。README からも設計書からも参照され続ける。
**「なぜこうなっているか」と「何を確かめていないか」は、公開物の一部として意味がある。**

### 2. **ADR を書くのは維持者。** 寄稿者には求めない

不具合の修正・テストの追加・誤字・小さな改善は、**ADR 無しでそのまま PR を出せる。**

寄稿者にお願いするのは 1 つだけ。

> **`docs/adr/` が決めたことを、黙って変えないこと。**

変えたい場合は Issue で「現状の決定がなぜ成り立たないか」を伝えてもらう。
**ADR はそれを受けて維持者が書く。**

### 3. 設計書の整合も**維持者の責任**にする

`docs/design/` と `00-traceability.md` の更新は、**寄稿者には必須にしない。**
直してもらえれば助かるが、「設計書は未更新です」と PR に書いてもらえればそれでよい。

**整合を寄稿者の善意に預けない。** 預けた時点で、整合は運任せになる。

### 4. 整合は **`main` への直接 push を禁じて**担保する

決定 2・3 で「寄稿者は ADR を書かなくてよい」とした以上、
**ずれに気づく場所を 1 箇所に作らないと、決定 2 がそのままずれの原因になる。**

`main` を GitHub のルールセットで保護し、**維持者自身も直接 push できないようにする。**

| 規則 | 効き目 |
|---|---|
| プルリクエストを必須にする | **すべての変更が、差分を見る場を 1 度は通る** |
| 承認数は **0** | **1 人で開発しているので、自分で作って自分でマージできる。** 止まらない |
| force push を禁じる | 履歴を書き換えられない |
| `main` の削除を禁じる | 消せない |
| バイパス者を**置かない** | 維持者も例外にしない。例外を作ると、急いでいるときに必ず使う |

**承認数を 0 にするのが要。** 1 以上にすると、1 人のリポジトリでは
**自分の PR を自分で承認できず、永久にマージできなくなる。**

### 5. PR テンプレートでは「書かせる」のではなく「気づかせる」

`.github/pull_request_template.md` に 1 行置く。

> **既存の決定に触れますか / Does this change a decision in `docs/adr/`?**
> - [ ] いいえ、または分からない（**そのままで構いません**）
> - [ ] はい（**どの ADR か**を下に書いてください。ADR は維持者が書きます）

**「分からない」を正解として用意する。** 寄稿者に調べさせない。
分からないまま PR が来ても、決定 4 の経路で維持者が必ず差分を見る。

## 影響

- `CONTRIBUTING.md` の §3・§4 と冒頭の「先に読んでほしいもの」を書き換えた
- `.github/pull_request_template.md` を足した
- `docs/adr/README.md:7` の維持者のローカルパスを消した
- ADR-0035 と `scripts/build-installer.ps1` から非公開リポジトリ名を外した
- **`main` への直接 push ができなくなる。** 維持者も `git push origin main` ではなく
  ブランチ → PR → マージの手順になる
- `ci.yml` の `build` / `docs` を**必須チェックにはまだしていない**（宿題）

## 実装で分かったこと（2026-11-14）

### 1. ルールセットは**最初の push より先に入れられない**

`main` がまだ存在しない状態で「プルリクエストを必須にする」を有効にすると、
**`main` を作る最初の push 自体が弾かれる。**
PR を出そうにも、ベースにする `main` が無い。

そこで**ルールセットは `enforcement: disabled` で先に作り**、
最初の push が通った後に `active` へ切り替える手順にした。
**設定は先に入れておき、効かせる瞬間だけ遅らせる。**

作ったルールセット:

| 項目 | 値 |
|---|---|
| リポジトリ | `MixedNutsJP/NutLens`（public） |
| 名前 | `protect-main` |
| ID | **27233358** |
| 規則 | `pull_request`（承認 0）/ `non_fast_forward` / `deletion` |
| バイパス者 | **なし** |
| 状態 | **`active`**（最初の push の直後に切り替えた） |

**最初の push の直後に `active` へ切り替えた**（2026-11-14）。

```powershell
gh api -X PUT repos/MixedNutsJP/NutLens/rulesets/27233358 -f enforcement=active
```

**実際に弾かれることを確かめた。** 手元で 1 コミット作って push した結果:

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
 ! [remote rejected] main -> main (push declined due to repository rule violations)
```

確認用のコミットは `git reset --hard origin/main` で巻き戻した（リモートには残っていない）。

### 3. GitHub が既定で入れてくる規則が 1 つある

作った直後に読み返すと、頼んでいない設定が入っていた。

```
require_extra_approval_for_unattributed_changes: true
```

**GitHub アカウントに結びついていないメールアドレスで作られたコミットに、
承認を 1 つ要求する。** 承認数 0 にした意味がここだけ消える。

誰にも承認できない PR が生まれる経路:

```
外部の寄稿者が、GitHub に登録していないメールで commit
  → その PR は「承認が 1 つ要る」状態になる
  → 1 人のリポジトリでは自分の PR を承認できない
  → **マージできない PR ができあがる**
```

**`false` にした。** 決定 4 の「止まらない」を保つため。

維持者自身のコミットは GitHub の noreply アドレスを使っているので元から引っかからない。**引っかかるのは外から来る PR だけ**で、
だからこそ気づきにくい。


### 2. 必須チェックは**ワークフローが `main` に載ってから**

`build` / `docs` を必須チェックに指定すると、GitHub はそのチェックの報告を待つ。
**`main` にワークフローが無い間は報告が来ないので、PR が永久に待ちになる。**

最初の push で `.github/workflows/ci.yml` が `main` に載り、
一度でも走って名前が確定してから足す。**それまでは入れない。**

**最初の push で CI が初めて走り、`build` と `docs` がどちらも成功した**（2026-11-14）。
名前が確定したので、同日に `required_status_checks` として足した。

## 宿題

- 第三者からの PR が実際に来たときの手触り（**事例が無い**）
- **PR を実際に 1 本も通していない。** 直接 push が弾かれることは確かめたが、
  **PR を作って必須チェックが効き、自分でマージできること**は未確認
- GitHub がルールセットの既定に**新しい規則を足してくること**がある
  （実装で分かったこと 3）。**作りっぱなしにせず、たまに読み返す**

## 却下した案

| 案 | 却下の理由 |
|---|---|
| `docs/adr/` を `.gitignore` に入れる | **README・CONTRIBUTING・SECURITY・CODE_SIGNING_POLICY・設計書・`ci.yml` の参照が全部切れる。** `ci.yml` の「全 ADR が索引にあるか」検査は常に失敗する。守れるのは個人のローカルパス 1 行だけで、**それは消せば済む** |
| ADR を必須のまま残す | **誤字 1 文字の PR にも ADR を要求することになる。** 利用者が「重い」と言ったのはこの状態 |
| ADR を任意にするだけで、ほかは何もしない | 利用者が指摘したとおり**実装とドキュメントがずれていく。** ずれに気づく場所がどこにも無い |
| 設計書の更新を寄稿者の必須にする | **整合を他人の善意に預けることになる。** 守られなかったときに気づく仕組みが無い |
| 承認数を 1 以上にする | **1 人のリポジトリでは自分の PR を承認できない。** マージが永久に止まる（決定 4） |
| 維持者をバイパス者に登録する | **急いでいるときに必ず使う。** 例外が常態になり、保護が無いのと同じになる |
| ルールセットを使わず、従来のブランチ保護を使う | 動きは同じだが、**ルールセットの方が履歴と適用範囲が見える。** 新しく作るなら後者 |
| 最初の push の前に `active` で作る | **`main` を作る push 自体が弾かれ、PR のベースも無い。** 入り口が塞がる（実装で分かったこと 1） |
| 最初から必須チェックを指定する | **`main` にワークフローが無い間、報告が来ず PR が永久に待ちになる**（実装で分かったこと 2） |
