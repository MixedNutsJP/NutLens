# ADR-0031. リリースはタグ駆動の GitHub Actions だけで作り、署名は差し込める段として空けておく

- 状態: **採用**（2026-11-14 承認）。**決定 4・5 は [ADR-0032](0032-ship-unsigned-and-keep-signing-vendor-neutral.md) が置き換えた**
- 日付: 2026-11-14

> **注記（2026-11-14）.** 承認の直後、利用者から
> 「署名は今後するか分からないし、SignPath を使用するとも限らない」と伝えられた。
> **決定 4（SignPath のアクションをコメントで置く）と決定 5（承認されるまでは未署名）は
> [ADR-0032](0032-ship-unsigned-and-keep-signing-vendor-neutral.md) に置き換わっている。**
> 決定 1・2・3・6・7 はそのまま効く。

## 背景

D-13「リリースのビルドは GitHub Actions で行い、**タグを打つとビルド・パッケージ作成・
GitHub Releases への公開まで自動で進む**ようにする（**署名サービスは信頼できるビルド環境
からの成果物を求めるため**）」

D-10「コード署名は **SignPath Foundation への申請**を前提に、**署名を差し込める構成**に
しておく。**承認されるまでは未署名で配布し**、README に SmartScreen の警告が出ることと
その回避手順を書く。署名の方針は `CODE_SIGNING_POLICY.md` にまとめる」

D-14「リポジトリに秘密情報を置かない。必要なものは GitHub Actions のシークレットで扱う」

決めるのは次の 3 つ。

1. 手元のビルドをリリースに使えてよいか
2. 署名が無い今、どう作っておくか
3. 版番号をどこで決めるか

**1 が効いてくる。** D-13 の括弧書きがその理由を言っている。
SignPath は「**どのソースから、どの CI で、どう作られたか**」が辿れる成果物にしか署名しない。
手元で作った zip を後から署名してもらう道は無い。

## 決定

### 1. リリースの成果物は GitHub Actions でしか作らない

手元の `vpk pack` は**動作確認のためだけ**に使う。
`dist/` と `release/` は `.gitignore` に入れ、手元の成果物をリポジトリに置かない。

**「手元で作って上げる」経路を残さない。**
残すと、急いでいるときにそちらを使い、署名が付かないものが公開される。

### 2. 引き金はタグだけ

```yaml
on:
  push:
    tags: [ 'v*' ]
  workflow_dispatch:      # 手で回せるが、公開はしない（成果物を見るだけ）
```

`main` への push ではリリースしない。**ビルドとテストだけ**を別のワークフローで回す。

### 3. 版番号はタグから取る。コミットに版を書かない

```
タグ v0.2.0 → Version = 0.2.0
```

`Directory.Build.props` の `<Version>` は**開発中の値**（`0.1.0`）のままにし、
リリースのビルドでは `-p:Version=` で上書きする。

**版を上げるコミットを作らない。** 作ると、
「タグの版」と「コミットの版」がずれたときに、**どちらが本物か分からなくなる。**

### 4. 署名は「空の段」として最初から置く

```yaml
      - name: Build
        run: dotnet publish ... -p:Version=${{ steps.version.outputs.value }}

      # --- 署名（SignPath の承認後に有効にする） ---
      # - name: Sign
      #   uses: signpath/github-action-submit-signing-request@v1
      #   with:
      #     api-token: ${{ secrets.SIGNPATH_API_TOKEN }}
      #     ...

      - name: Pack
        run: vpk pack ...
```

**順序が決まっている。** 署名は `publish` の後、`vpk pack` の**前**。
逆にすると、パッケージの中身を署名した後で再梱包することになり、**署名が壊れる。**

コメントアウトで置いておくのは、**後から「どこに入れるか」を考え直さないため。**
承認されたら、コメントを外して秘密情報を 1 つ足すだけにする。

### 5. 承認されるまでは未署名で配布し、**README に書く**

未署名の `Setup.exe` は Windows の SmartScreen が警告を出す。
**出ることを先に書いておく。** 書かないと、利用者は「怪しいソフト」と判断する。

回避手順（「詳細情報」→「実行」）と、**なぜ出るのか**（署名が無いため）を README に書く。
署名の方針は `CODE_SIGNING_POLICY.md` にまとめる（D-10）。

### 6. 秘密情報はワークフローのファイルに書かない

`${{ secrets.… }}` だけを参照する。必要なのは次の 2 つ（承認後）。

| 名前 | 用途 |
|---|---|
| `SIGNPATH_API_TOKEN` | SignPath へ署名を依頼する |
| `GITHUB_TOKEN` | Releases へ上げる（GitHub が自動で用意する） |

`.gitignore` に `*.pfx` `*.snk` `.env` が入っていることを確認済み（D-14）。

### 7. 配布に関わる値は `build/Distribution.props` 1 箇所に集める

owner / repo / 配布チャンネル / パッケージ ID。

**コードにも複数の yml にも散らさない。** リポジトリを移したときに直す場所を 1 つにする。

## 影響

- `.github/workflows/ci.yml`（push / PR でビルドとテスト）
- `.github/workflows/release.yml`（タグで公開）
- `build/Distribution.props`
- `CODE_SIGNING_POLICY.md`
- `.gitignore` に `dist/` `release/` を足す

## 宿題

- **ワークフローを一度も回していない。** リポジトリが無いので回せない
- **SignPath Foundation に申請していない。** 承認の条件（OSS であること、
  リポジトリが公開されていること）を満たしてから申請する
- `vpk` を GitHub Actions のランナーに入れる手順（`dotnet tool install -g vpk`。未検証）
- Windows ランナーで WPF のビルドが通るか（`windows-latest` で通るはずだが未検証）
- リリースノートをどう作るか（手書きか、コミットから生成するか。決めていない）

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 手元でビルドして Releases に上げる | **SignPath は「どのソースからどの CI で作られたか」が辿れる成果物にしか署名しない。** 後から署名してもらう道が無い（D-13 の括弧書きがその理由）。急いでいるときに使われ、署名の無いものが公開される（決定 1） |
| `main` への push ごとにリリースする | 公開物が増え続ける。利用者がどれを入れればよいか分からなくなる |
| 版を上げるコミットを作って、そこから版を取る | **タグの版とコミットの版がずれたときに、どちらが本物か分からなくなる**（決定 3） |
| 署名の段を後から足す | **入れる位置を忘れる。** `publish` の後・`vpk pack` の前という順序は、間違えると署名が壊れる形で表れる（決定 4） |
| 署名が取れるまでリリースしない | **D-10 が「承認されるまでは未署名で配布」と明示している** |
| SmartScreen の警告について書かない | 利用者は「怪しいソフト」と判断して止まる。**出ることが分かっていて黙るのは不親切**（決定 5） |
| 自己署名証明書で署名する | SmartScreen の警告は消えない（評判が無いため）。**「署名されている」という誤った安心を与える**だけ |
| owner / repo をワークフローに直接書く | リポジトリを移したときに直す場所が散る（決定 7） |
