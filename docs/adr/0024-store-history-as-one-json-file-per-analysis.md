# ADR-0024. 履歴を 1 解析 1 ファイルの JSON で持ち、結果を受け取った時点で書く

- 状態: **採用**（2026-11-14 承認）
- 日付: 2026-11-14

## 背景

F-28「履歴の一覧（第一候補・他の候補・日時・ユーザーのメモ）を見られる。
履歴は結果のテキストだけで作り、**画像のサムネイルは持たない**」

5.5「結果（候補・根拠・参考 URL）とユーザーのメモは履歴として残す
（`%LOCALAPPDATA%\NutLens\history\`）。履歴は設定画面から**個別・一括で消せる**」

置き場は要件で決まっている。決めるべきことは 4 つ。

1. 保存の形（1 ファイルにまとめるか、1 解析 1 ファイルか、データベースか）
2. **いつ書くか**
3. 何を書くか — より正確には、**何を書かないか**
4. 一覧をどう作るか

3 が効いてくる。履歴は**残るもの**で、一時データは**消えるもの**。
**境目を間違えると、「解析が終わったら消す」（5.5）が嘘になる。**

## 決定

### 1. 1 解析 1 ファイル。索引を持たない

```
%LOCALAPPDATA%\NutLens\history\
  2026-11-14T093012_<セッションID>.json
  2026-11-14T101745_<セッションID>.json
```

一覧はディレクトリを列挙して作る。索引ファイルを作らない。

**「個別に消せる」が、ファイルを 1 つ消すことになる。**
索引を持つと、索引と実体が食い違う状態が生まれ、
「消したのに一覧に残る」「一覧にあるのに開けない」が起きる。
その食い違いを直す仕組みを、また作ることになる。

ファイル名の先頭に日時を置くのは、名前の順＝新しい順に並べられるようにするため。

### 2. **結果を受け取った時点で書く。** 閉じるときではない

```
claude が返る → 履歴を書く → 結果画面を開く → 閉じる → 一時データを消す
                 ↑ ここ
```

閉じるときに書くと、**アプリが落ちたとき・強制終了されたときに、
利用枠を使って得た結果だけが消える。**
解析は利用者自身の Claude の利用枠を使っている（D-07）。やり直しは無料ではない。

再調査（F-27）で結果が変わったら、**同じファイルを上書きする。**
1 回の撮影に 1 つの履歴。再調査の回数だけ履歴が増えると、一覧が同じ作品で埋まる。

### 3. 書くのはテキストだけ。一時データから作ったものは書かない

| 書く | 書かない |
|---|---|
| 日時（撮影の開始） | **画像のサムネイル**（F-28 が明示的に禁止） |
| 第一候補・他の候補（題名・年・種別・確信度） | フレームのパス |
| 根拠・確認できなかった点・参考 URL | **文字起こし**（`transcript.txt`） |
| 利用者のメモ（URL・投稿者・キャプション・自由記述） | **OCR の結果**（`ocr.txt`） |
| 解析の情報（ターン数・所要時間・費用） | プロンプト・`claude.log`・`web_detection.json` |

**文字起こしと OCR を書かないのが、この決定でいちばん間違えやすいところ。**
どちらもテキストなので「サムネイルではないから残してよい」と読めてしまうが、
**撮影した音声・画像から作ったデータ**であり、5.5 の表では一時データの側にある。

> 画像（frames/）、音声（audio.wav）、**文字起こし、OCR の結果**、プロンプト、
> Claude Code のログ … 一時データ。…**自動的に完全に消す**

残すと「解析が終わったら消す」が嘘になる。

フレームのパスを書かないのは、**消えたはずのものを指す文字列が履歴に残り続ける**ため。

### 4. 版を持つ

```jsonc
{ "version": 1, "startedAt": "2026-11-14T09:30:12+09:00", … }
```

設定ファイルと同じく、後から形を変えられるようにする。
読めない版のファイルは**消さずに一覧から外す**（壊れた設定を退避するのと同じ扱い）。

### 5. 削除は `IHistoryStore` 1 クラスに閉じる

```csharp
public interface IHistoryStore
{
    IReadOnlyList<HistoryEntry> List();
    void Save(HistoryEntry entry);
    void Delete(string id);
    void DeleteAll();
}
```

一括削除は `history/` の中身を消す。**フォルダ自体は消さない**
（次の保存で作り直す手間と、消し漏れの判断が増える）。

消す処理を他所に書かない。5.5 で `ISessionWorkspace` に閉じたのと同じ理由。

## 影響

- `%LOCALAPPDATA%\NutLens\history\` が増える。**アンインストール時に残すかは利用者が選ぶ**（D-01）
- `IAppDataPaths` に `HistoryDirectory` が増える
- 履歴の保存は `AnalysisWorkflow`（解析の取り仕切り役）から呼ぶ
- 一覧と削除の画面は設定画面の中（5.5 が「設定画面から消せる」と書いている）

## 実装で分かったこと（2026-11-14）

### 1. `IAppDataPaths.HistoryRoot` は段階 1 から既にあった

影響の欄に「`IAppDataPaths` に `HistoryDirectory` が増える」と書いたが、
`HistoryRoot` として最初から用意してあった（5.5 が置き場を指定していたため）。
**増えたものは無い。**

### 2. 上書きのために、ファイル名ではなく ID で探す

ファイル名は `<日時>_<セッションID>.json` で、日時の部分は保存のたびに変わりうる。
名前から組み立てると**再調査のたびに別のファイルができる**ので、
`*_<ID>.json` で探して既存のファイルを使い回している。

テストで固定した（`同じIDで保存しても増えない`：ファイルが 1 つのままであることまで見る）。

### 3. 「残すもの／消すもの」の境目を 1 メソッドに閉じた

`HistoryEntry.From(id, savedAt, outcome, notes)` だけが履歴を組み立てる。
**引数に `SessionLayout` も文字起こしも OCR も取らない。**
取れるようにすると、うっかり詰められるようになる。

テストでは、生の出力（`RawOutput`）と観察した特徴が
直列化後の JSON に現れないことまで確かめている。

## 宿題

- **件数が増えたときの一覧の速さを測っていない。** 1 件 2〜5 KB の見込みで、
  1000 件でも 5 MB 程度だが、毎回全件を読んで並べる作りなので実測が要る
- 一覧の絞り込み・検索は作らない（要件に無い）。要るかどうかは使ってから
- 履歴の自動削除（古いものを消す）は**作らない。** 要件に無く、
  **利用者の記録を勝手に消す**ことになる

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 単一の `history.json` に配列で持つ | 1 件消すのに全体を読んで書き直すことになる。**書き込みの途中で落ちると履歴が全部消える。** 1 件の削除が全件を危険に晒す |
| SQLite を入れる | 依存が 1 つ増え、D-06 のライセンス確認と `THIRD_PARTY_NOTICES.md` の対象も増える。数百件の一覧に索引は要らない |
| 索引ファイル＋本体ファイル | 索引と実体が食い違う状態が生まれる。「消したのに一覧に残る」。その食い違いを直す仕組みをまた作ることになる（決定 1） |
| 結果画面を閉じるときに書く | **落ちたら、利用枠を使って得た結果だけが消える。** やり直しは無料ではない（決定 2） |
| 再調査のたびに新しい履歴を足す | 一覧が同じ作品で埋まる。1 回の撮影に 1 つ（決定 2） |
| サムネイルを持つ | **F-28 が明示的に禁止している。** 5.5 の「画像は一時データ」とも衝突する |
| 文字起こしと OCR も履歴に残す | **撮影した音声・画像から作ったデータなので、5.5 では一時データ側。** 残すと「解析が終わったら消す」が嘘になる（決定 3） |
| セッションフォルダを履歴として残す | 中身が一時データそのもの。5.5 に真っ向から反する |
| 古い履歴を自動で消す | 要件に無い。**利用者の記録を勝手に消す**ことになる。一括削除の口はある |
